Эволюция кодека инвойсов VoidPay

Как мы сжали полный крипто-инвойс в URL, помещающийся в QR-код

Проблема

Крипто-инвойсинг сломан. Отправка голого адреса кошелька через Telegram или Discord выглядит непрофессионально и опасно — перехват буфера обмена, неправильная сеть, ошибки в decimals токена. Существующие решения типа Request Finance требуют KYC, аккаунты и настройку организации.

VoidPay использует радикальный подход: URL и ЕСТЬ инвойс. Никакого бэкенда, базы данных, регистрации. Самодостаточная ссылка несёт все платёжные данные в hash fragment — невидимом для сервера, доступном только отправителю и получателю.

Ограничение

Полный инвойс (две стороны с именами, email, адресами, несколько позиций, налог, заметки) легко достигает 1КБ структурированных данных. Но URL имеют жёсткие лимиты: QR-коды становятся нечитаемыми свыше ~2000 байт, а старые HTTP-клиенты обрезают длинные URL.

Поскольку hash fragment несёт ВСЕ данные (принцип zero-backend), каждый байт инвойса должен уместиться в URL. Это ограничение привело к 7 итерациям кодека за 4 месяца.

Три эры сжатия

v0 (Базовый): JSON + lz-string. Просто, но расточительно — ключи JSON вроде "walletAddress" повторяются в каждом инвойсе, занимая ~40% места.

v1–v3 (Ad-hoc Binary): Ручные бинарные форматы. Каждая итерация добавляла оптимизации: сырые 20-байтные адреса (−22 байта каждый), битовые флаги для опциональных полей, словари валют, DEFLATE-сжатие текстовых блоков.

v4–v6 (TLV Structured): Формат Type-Length-Value, вдохновлённый BOLT12 из Lightning. Прямая совместимость, расширяемость, криптографические примитивы безопасности (salt для приватности, keccak256 domain separator для целостности). v6 добавляет Brotli-сжатие всего payload для максимальной плотности.

С 1043 символов (v0) до 698 символов (v6) для полного инвойса со всеми полями — на 33% меньше, при этом добавлены salt, domain separator и прямая совместимость.

Нововведения
+Гибридная архитектура: бинарное для структурированных данных, блоб для текста

−Нет криптографических примитивов (salt, domain separator)

−Base62: расширение 1.37× (vs 1.33× для Base64url)

Type-Length-Value записи: каждое поле самоописывается (тип=1Б, длина=uint16, значение=NБ)
Нововведения
+TLV формат: прямая совместимость (неизвестные типы безопасно пропускаются)
+Salt (16Б): приватность — одинаковый инвойс создаёт разные URL

−4-байтный заголовок: [MAGIC, VERSION, 0x00, COUNT]
−DEFLATE только на опциональных текстовых полях (обязательные не сжимаются)
💡 TLV формат — архитектурный прорыв: он делает кодек расширяемым. Новые типы полей можно добавлять не ломая старые декодеры. Но оверхед безопасности (50 байт) делает маленькие инвойсы значительно больше.

+Brotli q11: ~20% лучше DEFLATE на типичных данных

−Обязательные поля (имена, позиции) вне области сжатия
💡 Мантисса-кодирование — главный выигрыш для сумм: "500000000000000000" (18 символов текстом) становится мантисса=5 + экспонента=17 → всего 2 байта. Это важно, потому что крипто-суммы routinely имеют 18 десятичных знаков.

Нововведения
